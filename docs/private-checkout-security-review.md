# Private checkout hardening — PR #71

Decision: preserve the private, automatic flow at `efdd5971`. Students never see
affiliate questions, codes, percentages or confirmation dialogs. Capture does
not claim for the ambient account. Normal login, Google account selection,
registration, form/school onboarding and the existing payment-return display
are retained. `MoonExplorer86/Academy-partners` owns programme management and
payout policies; this change does not move that ownership.

## Changes

- The Edge Function reads database attribution even when a direct caller omits
  both referral fields. Eligible attributed payments require the private signed
  server assertion before payment insertion. It is checked against the verified
  purchaser, immutable partner, expiry, MAC and checkout key. An unexpected
  payment link created during a lookup/insert race also blocks provider access.
- A successful/existing claim with a missing read-back row is an error, not
  permission to create an unattributed bill. Verified ineligible/non-referral
  purchasers still use ordinary checkout. The browser sees only generic errors.
- Cookie-authenticated checkout POSTs require the exact serving origin and reject
  cross-site fetch metadata, including on previews. OAuth/PKCE is unchanged.
- The existing atomic `ON CONFLICT DO NOTHING RETURNING` bill ownership stays.
  Browser attempts retain an account-scoped idempotency key through retries,
  reloads and ambiguous provider/database failures. Matching, authenticated
  terminal payment-return results release it for a subsequent purchase/renewal.
  Unknown outcomes are never automatically given a replacement key/bill.
- A delayed response started by account A cannot redirect newly signed-in B to
  A's bill or consume the private reference B still needs. Unmounting the
  checkout page invalidates that response too.
- There is no browser consent cookie in this approved flow, hence no stale
  consent dialog/marker to restore or invalidate. A fresh private proof is
  generated by the server for each checkout, bound to its user and key.
- Two existing TypeScript failures are fixed by one missing-value guard in each
  Science test. No lesson source, rendering, question bank or feature changed.

## Remaining risks and release gate

- Independent deliberately supplied checkout keys remain distinct transactions;
  the existing API is not a global per-user payment lock. Cross-tab/device
  deduplication is not claimed. Uncertain same-key attempts require provider
  reconciliation, not deletion, callback replay or automatic replacement.
- Blocked/corrupt browser session storage produces a generic checkout failure
  before creating a bill. The existing 60-day first-touch local-storage lifetime
  is unchanged; cross-origin OAuth storage is not assumed to be shared.
- Actual mobile Safari/Chrome Google OAuth and a fresh hosted sandbox run were
  not performed on this revision. Preserve the correct Auth redirect allowlist
  and return-origin configuration; do not switch to live payment keys here.
- Full-suite baseline failures must be reported separately from the passing
  security checks. Keep PR #71 draft and do not merge/deploy in this task.

## Environment, safe rollout and rollback

No new environment variable. Retain the same high-entropy, server-only
`PARTNER_CONFIRMATION_SECRET` in web and Edge (at least 32 random bytes; never
`VITE_`). Existing Supabase settings, `TOYYIBPAY_SECRET_KEY`, category,
`APPLICATION_URL`, and exact `PAYMENT_RETURN_PREVIEW_ORIGINS` remain required.
No credential was printed, committed, rotated or set by this task.

After separate approval: verify the existing migration history and matching
settings, stage both web and Edge revisions, then run the account-A → account-B
private OAuth/onboarding/checkout/return/admin scenario plus direct-API negative
and concurrent-request checks. For a coordinated production release, update web
first (old Edge accepts the extra signed checkout-key field), then Edge, and
reload cached clients to activate safe browser retries. New Edge rejects old
unbound proofs, so do not leave mixed server revisions running.

Rollback: pause new checkouts, retain fail-closed Edge verification and all
existing payment records/keys, then roll back or repair web/Edge coherently.
Never weaken RLS, remove verification, reset uncertain attempts or replay paid
callbacks to restore availability. There is no database rollback in this change.

Recommendation: **GO for PR review, NO-GO for merging/deploying in this task**.
Review the unrelated baseline failures and obtain a fresh hosted acceptance run
and explicit release authorization. The passing security/build checks do not
mean the entire application suite is green.
